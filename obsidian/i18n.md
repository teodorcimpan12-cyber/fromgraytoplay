# i18n

Three languages: Romanian (default), English, Hungarian.

## The `T` dictionary

A plain object literal at `index.html` line 184:

```js
const T = {
  ro: { home: "Acasă", courts: "Terenuri", ... },
  en: { home: "Home",  courts: "Courts",   ... },
  hu: { home: "Kezdőlap", courts: "Pályák", ... }
};
```

Strings are flat (no nesting). Used as `T[lang].key`.

## Language switching

Cycle: `ro → en → hu → ro`. Function: [[Helpers/nextLang]].

The label on the language button shows the **next** language code, not
the current one — so `RO` button shows `EN` (because clicking moves you
to English).

```js
function nextLang(l) {
  return l === "ro" ? "en" : l === "en" ? "hu" : "ro";
}
```

`lang` is stored in [[Architecture]] `AppCtx`. Also persisted to
`localStorage.fgtp_lang` so it survives reload.

## Long-form prose

Separate from `T` so the dictionary stays scannable:

- `ESSAY = { ro: "...", en: "...", hu: "..." }` — the project's manifesto.
- `TIMELINE = [{ ro: {...}, en: {...}, hu: {...} }, ...]` — historical
  beats per entry.

## Adding a new string

Per the brief's "checklist for adding a feature":

1. Add the key to **all three** language objects (`T.ro`, `T.en`, `T.hu`).
2. If the HU translation is auto-translated or uncertain, mark the
   string with a `// TODO: HU review` comment so a native speaker can
   sweep them.
3. Reference it in code as `T[lang].newKey`.

## Hungarian status

HU strings are **draft**. The brief is explicit: "don't machine-translate
— find a Hungarian-speaking classmate or use the Hungarian student
association at your school." Until that review happens:

- Don't push HU prose changes that change meaning without flagging them.
- Diacritics matter: test with `á é í ó ö ő ú ü ű`.

## Date/number formatting

The live site does not currently use locale-aware date or number
formatting. The Vite scaffold ([[vite-next/Source code]]) uses `date-fns`
with the `ro` / `hu` / `enUS` locales — adopt that pattern when migrating.
